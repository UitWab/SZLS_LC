# 智能建梁数字孪生平台数据库 V4 梁位工单设计决策

## 1. 范围

V4 只增加 A 模块负责的梁位工单数据能力。梁位工单暂时定义为梁场内部的入位、移位和出位任务，用于记录计划并在完成时原子更新梁的当前位置。

V4 不实现 B 的 HTTP 路由、登录鉴权、岗位权限、页面、调度算法、审批、派工、消息广播或设备控制，也不扩展为通用工作流引擎。

## 2. 核心决策

1. 使用专用表 `beam_position_work_order`，不建立高耦合的通用工单表。
2. 工单类型为 `PLACE`、`MOVE`、`RELEASE`。
3. 状态为 `PENDING`、`IN_PROGRESS`、`COMPLETED`、`CANCELED`。
4. 类型和状态以字符串保存，不使用 MySQL ENUM 或数据库 CHECK 固化，便于口径变化后通过新版本扩展。
5. 创建工单时快照记录原梁位和目标梁位，但不预占目标梁位。
6. 完成工单时锁定梁，核对当前梁位仍等于原梁位，再执行实际梁位变更。
7. 梁位变更和工单完成在同一事务内提交；占用冲突或校验失败时一起回滚。
8. 同一根梁最多有一个 `PENDING` 或 `IN_PROGRESS` 工单。Service 通过锁定梁记录串行化创建，避免依赖 MySQL 不支持的条件唯一索引。
9. 工单创建后不提供任意业务字段更新，只允许开始、完成和取消状态流转。
10. 不提供物理删除工单。

## 3. 类型约束

- `PLACE`：梁当前必须没有梁位，必须提供目标梁位。
- `MOVE`：梁当前必须已有梁位，必须提供不同于原梁位的目标梁位。
- `RELEASE`：梁当前必须已有梁位，不允许提供目标梁位。

创建时保存的 `source_position_id` 是业务快照。完成时若梁的实际当前位置已经变化，工单拒绝完成，避免旧任务覆盖新状态。

## 4. 状态流转

允许的流转为：

- `PENDING -> IN_PROGRESS`
- `PENDING -> CANCELED`
- `IN_PROGRESS -> COMPLETED`
- `IN_PROGRESS -> CANCELED`

完成或取消后的工单不可再次流转。`started_at` 在开始时写入，`finished_at` 在完成或取消时写入，时间统一使用无时区标记的 UTC `DATETIME(6)`。

## 5. 分层与对外契约

- Model 只描述持久化结构。
- Schema/DTO 负责输入约束和稳定输出，不返回 ORM。
- CRUD 只查询、创建、分页和执行受限状态字段更新，不提交事务。
- Service 负责项目范围、引用校验、并发锁、状态流转和事务。
- B 只通过 `create_database_services().position_work_orders` 调用。

V4 保留既有 `beams.assign_position`、`move_beam`、`release_position` 以兼容 V1/V2，但 B 执行某一梁位工单时不得再额外调用这些方法重复变更梁位。

## 6. 后续变化策略

若业务口径调整，优先新增类型、状态、可空字段或独立关联表，并通过 Alembic 向前迁移。除非出现已确认的跨领域共同规则，不把梁位工单扩展成通用审批或任务引擎。设备执行、操作人员、审批链、优先级和调度批次暂不建模，待明确需求后再独立评估。
