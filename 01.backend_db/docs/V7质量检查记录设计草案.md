# 智能建梁数字孪生平台数据库 V7 质量检查记录设计草案

- 文档状态：已按确认方案完成开发，待独立测试、审计与冻结
- 计划版本：V7.0
- 依赖基线：`backend-db-v6.0.0`
- 目标数据库：MySQL 8.0

## 1. 需求依据与目标

V7 依据《业务记录域暂行规则》和《业务记录域分期开发计划》中已经明确的质量检查需求设计，不扩展未确认的业务。

一条质量检查记录表示对一片梁进行的一次独立检查或验收事实。它保存整体结论和可选的检查项明细，并可关联工序或 V6 中某次已结束的工序执行记录。

V7 的目标是让 A 模块稳定保存、查询、复检和受控作废质量事实，同时给未来专用检查模板留下向前扩展空间。

## 2. 范围边界

### 2.1 V7 实现

- 质量检查主记录及检查项明细；
- 记录、单条读取、条件筛选、页码分页和受控作废；
- 项目、梁、工序、V6 工序执行记录和操作用户引用校验；
- 复检记录对既有检查记录的引用；
- 执行编码及外部来源幂等；
- DTO、CRUD、Service、公开 Python Protocol、组合工厂入口；
- Alembic 迁移、测试、数据字典、A-B 接入文档和审计交接资料。

### 2.2 V7 不实现

- 质量计划、待检任务、审批流、会签、电子签章或自动放行；
- 检查模板配置、动态表单设计器或质量规则引擎；
- 图片、附件、报告文件或二进制存储；
- 不合格处置单、返工工单或责任追踪流程；
- 自动修改梁状态或自动追加 V5 生命周期事件；
- HTTP、登录鉴权、岗位权限、页面、消息队列或通知；
- 运输、设备、告警、二维码、RFID 和设备时序测点。

这些能力没有明确数据契约，不能借 V7 提前开发。

## 3. 数据模型

V7 使用两个专用表，不建立通用业务记录表、通用检查基类或无约束 JSON 载荷。

### 3.1 `beam_quality_inspection`

| 字段 | 建议类型 | 空值 | 规则 |
|---|---|---|---|
| `id` | `BIGINT` | 否 | 内部主键，自增 |
| `project_id` | `BIGINT` | 是 | 跟随梁项目；兼容 V1 全局梁 |
| `inspection_code` | `VARCHAR(64)` | 否 | 全表唯一，创建后不可修改 |
| `beam_id` | `BIGINT` | 否 | 被检查的梁 |
| `process_definition_id` | `BIGINT` | 是 | 可选关联工序 |
| `process_execution_id` | `BIGINT` | 是 | 可选关联 V6 工序执行记录 |
| `previous_inspection_id` | `BIGINT` | 是 | 可选关联同一梁的既有检查记录，表示复检 |
| `inspection_type_code` | `VARCHAR(64)` | 否 | 开放的稳定类型代码，不使用 MySQL ENUM |
| `result_code` | `VARCHAR(32)` | 否 | 第一版仅 `PASS`、`FAIL` |
| `inspected_at` | `DATETIME(6)` | 否 | B 提供的 UTC 检查时间 |
| `actor_user_id` | `BIGINT` | 是 | 可选平台用户 |
| `actor_name` | `VARCHAR(128)` | 是 | 检查人名称快照 |
| `source` | `VARCHAR(32)` | 否 | `MANUAL`、`SYSTEM`、`IMPORT`、`DEVICE` |
| `external_record_id` | `VARCHAR(128)` | 是 | 外部幂等标识 |
| `summary` | `VARCHAR(500)` | 是 | 结论摘要，不保存敏感信息 |
| `is_voided` | `BOOLEAN` | 否 | 默认 `FALSE` |
| `voided_at` | `DATETIME(6)` | 是 | 首次作废时间 |
| `voided_by_user_id` | `BIGINT` | 是 | 可选作废用户 |
| `voided_by_name` | `VARCHAR(128)` | 是 | 作废人名称快照 |
| `void_reason` | `VARCHAR(500)` | 是 | 作废时必填 |
| `created_at` | `DATETIME(6)` | 否 | A 写入 UTC |
| `updated_at` | `DATETIME(6)` | 否 | 正常只因作废变化 |

所有外键使用 `RESTRICT`。不在主表保存梁、工序或执行记录的业务编码副本，对外 DTO 在事务内通过关联转换为业务编码。

### 3.2 `beam_quality_inspection_item`

| 字段 | 建议类型 | 空值 | 规则 |
|---|---|---|---|
| `id` | `BIGINT` | 否 | 内部主键，自增 |
| `inspection_id` | `BIGINT` | 否 | 关联质量检查主记录，删除规则 `RESTRICT` |
| `item_code` | `VARCHAR(64)` | 否 | 本次检查内稳定且唯一，精确区分大小写 |
| `item_name` | `VARCHAR(128)` | 否 | 检查项目名称快照 |
| `requirement_text` | `VARCHAR(500)` | 是 | 验收要求快照 |
| `observed_value` | `VARCHAR(128)` | 是 | 实际值文本 |
| `unit` | `VARCHAR(32)` | 是 | 单位快照 |
| `result_code` | `VARCHAR(32)` | 否 | `PASS`、`FAIL`、`NOT_APPLICABLE` |
| `remark` | `VARCHAR(500)` | 是 | 检查项说明 |

使用 `(inspection_id, item_code)` 唯一约束。`item_code` 是精确、区分大小写的稳定标识，`ITEM` 与 `item` 表示两个不同检查项。第一版不增加数值、上下限、模板 ID 或排序字段；检查项按 `item_code` 稳定返回。未来真实模板明确后，再以新字段或独立模板表向前扩展。

## 4. 核心业务规则

### 4.1 项目与梁

- `project_id` 始终跟随梁的实际项目归属；B 只提交 `project_code` 和 `beam_code`。
- `project_code=None` 只访问全局梁及其质量记录。
- 项目级调用只访问本项目记录，跨项目读取统一表现为记录不存在。
- 停用项目不能新增质量记录；既有记录仍可读取和作废。

### 4.2 工序及 V6 执行记录

- 可只关联工序，也可关联具体 V6 执行记录，二者都可以为空。
- 项目梁只能关联同项目工序或平台通用工序；全局梁只能关联通用工序。
- 提供 `process_execution_code` 时，执行记录必须与质量记录属于同一项目、同一梁。
- 同时提供 `process_code` 时，它必须与执行记录关联的工序一致；未提供时由执行记录确定工序。
- 已作废的 V6 执行记录不能用于新建质量记录。
- V6 执行记录以后被作废时，不自动作废或修改已有质量记录，避免从 V7 反向改变冻结的 V6 行为；是否作废质量记录由 B 根据业务决定。
- 工序或执行记录停用、作废前形成的质量历史仍可查询。

### 4.3 整体结果与检查项

- 检查项可以为空，以兼容只保存整体验收结论的场景。
- 存在检查项时，只要任一检查项为 `FAIL`，主记录不得为 `PASS`。
- 主记录为 `FAIL` 时，不强制必须存在失败检查项；整体失败原因可能记录在 `summary` 中。
- `NOT_APPLICABLE` 不视为失败。
- 主结果由 B 明确提交，A 只执行上述一致性校验，不建设质量判定引擎。

### 4.4 复检

- 复检创建新记录，通过 `previous_inspection_code` 指向同项目、同一梁的既有质量记录。
- 不要求前一记录必须为 `FAIL` 或已作废，A 不推断复检原因。
- 质量记录创建后不可修改，因此引用只能指向已经存在的记录，天然不能指向自身或未来记录；Service 仍执行项目和梁一致性检查。
- 第一版允许同一历史记录产生多条复检分支，不增加“只能有一个直接复检”的未确认约束。
- 复检关系不等同于录入纠错；录入错误仍按“作废原记录并新建正确记录”处理。

### 4.5 操作人、时间和来源

- `actor_user_id` 与 `actor_name` 至少提供一个。
- 提供用户 ID 时用户必须存在；未提供名称时保存用户当前显示名称快照。
- A 不检查用户是否具有质量岗位权限，权限由 B 调用前判断。
- `inspected_at` 由 B 以 UTC 提供，A 不用 `created_at` 代替业务时间。
- `source` 复用 V6 的 `RecordSource` Schema 枚举，不抽取通用 ORM 或 Service 基类。

## 5. 幂等、作废与不可变性

### 5.1 幂等

- `inspection_code` 全表唯一。
- 提供 `external_record_id` 时，`source + external_record_id` 在质量检查主表内唯一。
- 相同幂等标识且主记录、复检关系及全部检查项业务内容一致时，返回既有记录。
- 内容不一致时返回 `ResourceConflictError`，不覆盖原记录。
- 检查项顺序不属于业务内容；幂等比较以精确 `item_code` 为键，检查项代码重复或内容不同均视为冲突。
- 并发重复请求以数据库唯一约束兜底，并在新事务中恢复既有结果。
- 与 V6 相同，资源后续停用不影响完全相同请求返回既有记录；只在确实新增时检查启用和作废状态。

### 5.2 作废

- 主记录和检查项创建后均不提供任意更新或物理删除。
- `void` 锁定主记录，首次写入作废时间、操作人和原因。
- 重复或并发作废返回首次结果，不覆盖首次作废信息。
- 作废主记录不会删除或逐项修改检查项；检查项随主记录整体视为无效。
- 已作废记录不能恢复。

## 6. DTO 与公开接口

### 6.1 Schema/DTO

- `BeamQualityInspectionCreate`：主记录、可选关联编码及检查项列表；
- `BeamQualityInspectionItemCreate`：单个检查项输入；
- `BeamQualityInspectionVoid`：作废操作人和原因；
- `BeamQualityInspectionFilter`：列表筛选；
- `BeamQualityInspectionSummary`：列表主记录摘要，不携带检查项；
- `BeamQualityInspectionRead`：完整主记录和只读检查项列表；
- `BeamQualityInspectionItemRead`：检查项输出；
- `BeamQualityResult`、`BeamQualityItemResult`：稳定字符串枚举；
- `BeamQualityInspectionSortField`：受控排序字段。

DTO 只返回 `project_code`、`beam_code`、`process_code`、`process_execution_code` 和 `previous_inspection_code` 等业务编码，不返回 ORM、Session 或内部关联 ID 作为 B 的业务依赖。

### 6.2 B 的调用形式

公开入口建议为 `database_services.quality_records`：

| 方法 | 作用 |
|---|---|
| `record(data)` | 原子创建主记录及全部检查项，支持幂等 |
| `get(inspection_code, project_code=...)` | 在项目范围读取完整记录及检查项 |
| `list(filters, page_request, sort_by, sort_order)` | 查询主记录摘要 |
| `void(inspection_code, data, project_code=...)` | 受控作废，重复调用幂等 |

不提供 `update`、`delete`、`approve`、`release`、`upload` 或任意结果赋值接口。

## 7. 查询与分页

第一版主记录筛选支持：

- 项目编码；
- 梁编码；
- 工序编码；
- V6 工序执行编码；
- 检查类型代码；
- 多个整体结果；
- 多个来源；
- 检查时间范围；
- 是否复检；
- 是否作废；
- 操作用户 ID；
- 外部记录标识；
- 检查编码、梁编码、操作人名称和摘要关键词。

使用既有 `PageRequest` 和 `PageResult`，页大小 1 至 100。默认按 `inspected_at DESC, id DESC` 排序，其他排序字段也追加同方向 `id`。

列表不连接并展开检查项，避免一对多关联破坏分页计数。检查项只由 `get` 随主记录完整返回。V7 没有明确的增量消费需求，因此不新增游标接口。

## 8. 约束与索引

建议数据库约束：

- 主表：`inspection_code` 唯一；
- 主表：`(source, external_record_id)` 唯一，允许多个 `NULL`；
- 子表：`(inspection_id, item_code)` 唯一；
- 主表：作废字段一致性检查约束；
- 所有外键删除规则为 `RESTRICT`。

建议索引：

- `(project_id, inspected_at, id)`；
- `(beam_id, inspected_at, id)`；
- `(process_definition_id, inspected_at, id)`；
- `(process_execution_id)`；
- `(previous_inspection_id)`。

不提前为检查项文本、车辆、设备或未来模板创建索引。

## 9. 事务与并发

- `record` 在一个事务中完成引用解析、幂等检查、主结果与检查项一致性校验、主表插入、检查项批量插入和 DTO 转换；任一步失败全部回滚。
- 幂等创建只依赖质量记录自己的唯一约束，不锁梁，也不阻止同一梁并行产生不同检查记录。
- `void` 使用主记录行锁保护首次作废结果。
- V7 读取冻结的 V6 执行事实，不修改 V6 Service，也不让 V6 反向依赖 V7。
- 不自动修改梁、工序执行记录、生命周期事件或操作审计日志。

## 10. 异常契约

只新增一个领域不存在异常：

- `BeamQualityInspectionNotFoundError`，代码 `beam_quality_inspection_not_found`。

其他情况复用现有公共异常：

- 项目、梁、工序、执行记录或用户不存在时使用对应 NotFound 异常；
- 跨项目资源、复检梁不一致、结果与检查项矛盾、幂等内容不同使用 `ResourceConflictError` 或 `InvalidDataError`；
- 停用项目、停用工序使用 `InactiveResourceError`；
- 数据库连接和 SQL 异常继续由统一数据库异常转换处理。

## 11. 测试与审计计划

### 11.1 必测功能

- 有检查项和无检查项的 `PASS`、`FAIL` 记录；
- 检查项失败时主记录不得通过；
- 项目、梁、全局资源和工序作用域；
- V6 执行记录关联的一致性及已作废执行拒绝；
- 复检同项目同梁校验及允许分支；
- 编码和外部标识幂等、不同内容冲突；
- 检查项顺序变化仍保持幂等；
- 创建、DTO 转换和检查项写入失败全部回滚；
- 作废、重复作废和并发作废；
- 筛选、稳定分页、字符串和时间边界；
- ORM/迁移约束与完整回归。

### 11.2 审计重点

- 不暴露 ORM、CRUD、Session 或内部 ID；
- 不出现跨项目梁、工序、执行记录或复检引用；
- 幂等恢复不被资源后续停用破坏；
- 一对多检查项不破坏分页和总数；
- 不修改冻结的 V6 行为，不产生梁状态或事件副作用；
- 不进入 B 的鉴权、审批、附件和页面范围。

2. 编写 V7 数据字典和 Alembic 迁移；
3. 实现独立 ORM 与 Schema；
4. 实现 CRUD 查询和原子主从写入；
5. 实现 Service 的引用、一致性、幂等和作废规则；
6. 增加公开 Protocol 与组合工厂入口；
7. 完成定向、并发、迁移和全量测试；
8. 更新 A-B 契约并交给独立测试、审计；
9. 问题关闭后单独冻结 V7。

## 13. 已确认的暂行决策

以下方案已经随“按照 V7 计划开始开发”的授权进入本版实现：

1. 允许没有检查项、只保存整体结论的质量记录；
2. `inspection_type_code` 暂不设固定清单，由 B 使用稳定字符串；
3. 整体结果只有 `PASS`、`FAIL`，不增加“待定”“有条件通过”；
4. 已作废 V6 执行记录不能用于新建质量记录，但执行记录后续作废不联动作废质量记录；
5. 复检允许多分支，不要求前一记录失败或作废；
6. 检查项顺序不参与业务语义，按 `item_code` 稳定返回；
7. 继续兼容全局梁的质量记录；
8. V7 不提供游标增量查询。

后续真实业务要求发生变化时，通过 V8 或后续版本向前迁移调整，不改写已经保存的数据含义，也不影响冻结的 V6。
