# 智能建梁数字孪生平台 V2 数据库数据字典 项目与权限基础域

- **版本：** V2.0 候选交付版
- **数据库：** MySQL 8.0.x
- **ORM 与迁移：** SQLAlchemy 2.x 与 Alembic
- **当前迁移版本：** `e5c1a7b3d902`
- **当前范围：** V1 梁场基础域，以及 `project`、`process_definition`、`app_user`、`user_credential`、`auth_role`、`auth_permission`、`auth_role_permission`、`auth_user_role`、`project_member`、`project_member_role`
- **基础单位：** 长度和坐标 mm；质量 kg；业务时间 UTC

## 当前约定

- `beam_position` 表示最小、唯一、单梁占用的梁场物理梁位。
- `beam.current_position_id` 仅为梁当前所在梁场物理梁位的唯一真源，不代表运输、到场或架设阶段的位置。
- `beam.status` 使用稳定的大写字符串代码，当前代码清单见“梁状态代码”。数据库字段保持 `VARCHAR(32)`，便于后续新增或废弃状态。
- `created_at` 和 `updated_at` 由 ORM 在应用侧写入无时区标记的 UTC 时间。MySQL 字段本身没有服务器默认值。
- `is_active` 的应用默认值为 `TRUE`，但 MySQL 字段没有服务器默认值。
- `beam.status` 的应用默认值为 `UNPRODUCED`，但 MySQL 字段没有服务器默认值。
- V2 不生成默认项目、用户、角色或权限数据。
- `beam_type.project_id`、`yard_area.project_id` 和 `beam.project_id` 在过渡期允许为空，等待真实项目编码和存量数据归属确认后再回填。
- 密码明文、登录会话和令牌不保存于 A 数据库模块；`user_credential` 只保存 B 生成的密码散列。
- 角色范围使用稳定字符串 `SYSTEM` 或 `PROJECT`，不使用 MySQL ENUM。

## 仍待确认

- `area_type` 的允许代码清单。
- `production_date` 的业务口径，例如浇筑日期或成品完成日期。
- 场地业务坐标的原点、轴方向和坐标系版本。
- 一梁一码中的不可变梁身份、二维码和 RFID 标识的数据模型。
- 工序流转、生产任务与梁状态之间的业务编排规则。

## 表关系

| 父表或实体 | 子表或实体 | 关系 | 说明 |
|---|---|---|---|
| `yard_area` | `beam_position` | 1 : N | 一个区域包含多个梁位；每个梁位属于一个区域。 |
| `yard_area` | `yard_area` | 1 : N 可选 | 通过 `parent_id` 支持区域层级；顶层区域 `parent_id` 为空。 |
| `beam_type` | `beam` | 1 : N | 一种梁型可对应多片梁；每片梁对应一个梁型。 |
| `beam_position` | `beam` | 0..1 : 0..1 | 一片梁当前最多占用一个梁位；一个梁位最多被一片梁占用。 |
| `project` | `beam_type`、`yard_area`、`beam` | 1 : N 可选 | V2 过渡期子表的 `project_id` 可空。 |
| `app_user` | `user_credential` | 1 : 0..1 | 用户基础资料与认证凭据隔离。 |
| `auth_role` | `auth_permission` | N : M | 通过 `auth_role_permission` 建立角色权限。 |
| `app_user` | `auth_role` | N : M | 通过 `auth_user_role` 建立系统级角色。 |
| `project`、`app_user` | `project_member` | 1 : N | 一个用户可以加入多个项目。 |
| `project_member` | `auth_role` | N : M | 通过 `project_member_role` 建立项目级角色。 |
| `project` | `process_definition` | 1 : N 可选 | 工序可以是平台通用工序，也可以归属于具体项目。 |

## 一梁一码与生命周期扩展边界

当前四张表只覆盖梁场基础档案和当前状态，不等同于完整生命周期模型。

- `beam.id` 是数据库技术主键。
- `beam.beam_code` 是稳定业务梁号。
- 二维码和 RFID 是现场识别媒介，不应直接替代技术主键或业务梁号。
- 是否新增不可变 `beam_uid`，以及二维码、RFID 是否采用独立身份表，需要在手持设备和生命周期模块开发前单独确认。
- `beam.current_position_id` 只表达当前梁场梁位。运输轨迹、到场位置、架设位置和历史移动记录应由后续事件或位置历史模型承担。
- V1 不提供梁删除接口。生命周期历史和审计数据不得通过删除梁实现清理。

## V2 基础设计规范

- **DB-01**：表名采用小写单数 snake_case。
- **DB-02**：ORM 类采用 PascalCase。
- **DB-03**：普通业务表主键统一命名为 `id`。
- **DB-04**：主键默认 `BIGINT AUTO_INCREMENT`。
- **DB-05**：业务编码与技术主键分离；业务编码按需 UNIQUE。
- **DB-06**：外键统一命名为 `<entity>_id`。
- **DB-07**：核心业务外键默认禁止级联删除。
- **DB-08**：字段默认 NOT NULL，只有确有未知或不存在语义时允许 NULL。
- **DB-09**：时间字段统一使用 `*_at` 或 `*_date` 命名。
- **DB-10**：业务时间统一使用 `DATETIME(6)`，数据库内按 UTC 解释。
- **DB-11**：不全局采用软删除；基础档案优先使用 `is_active`。
- **DB-12**：状态字段使用 VARCHAR 保存稳定代码；当前代码清单需版本化维护，不使用 MySQL ENUM。
- **DB-13**：几何尺寸和坐标基础单位为 mm，质量基础单位为 kg。
- **DB-14**：大文件不直接保存到 MySQL。
- **DB-15**：索引根据真实查询场景设计，不机械给所有字段建立索引。
- **DB-16**：默认采用规范化关系设计；同一事实尽量只有一个真源。
- **DB-17**：数据库完整性通过 PK、FK、UNIQUE、NOT NULL 等约束兜底。
- **DB-18**：所有表结构修改通过 SQLAlchemy ORM 和 Alembic 管理，不手工 ALTER 共享数据库。
- **DB-19**：`beam.current_position_id` 仅表示当前梁场物理梁位，不作为运输、到场或架设位置的全局真源。
- **DB-20**：数据库技术主键、梁业务编号、二维码和 RFID 标识必须区分；身份扩展另行设计。
- **DB-21**：V1 不提供梁删除接口；历史与审计数据不得通过删除梁实现清理。
- **DB-22**：数据字典应区分数据库默认值与应用默认值；应用默认不等同于 MySQL DEFAULT。
- **DB-23**：普通用户 DTO 与认证凭据 DTO 必须隔离，密码散列不得出现在普通查询结果。
- **DB-24**：系统角色和项目角色分别通过独立关联表分配，Service 校验角色范围。
- **DB-25**：角色、权限、用户和项目成员使用启停状态，不提供物理删除接口。
- **DB-26**：有效权限由启用的系统角色权限与指定项目内启用的项目角色权限合并并去重。
- **DB-27**：工序定义只表达可配置基础资料和显示排序，不在数据库层固化生产流程状态机。

## 索引说明

当前索引覆盖业务编码、外键和梁位唯一占用约束。后续只有在 B 的真实查询或增量同步方案确认后，才评估增加 `beam(status, id)`、`beam(updated_at, id)` 等索引。

## 模块边界

本数据字典属于 A 数据库模块。A 负责表结构、迁移、ORM、数据访问、数据库约束和数据字典；FastAPI、登录鉴权、Redis、MQTT、WebSocket、扫码设备通信、RFID 设备通信、业务流程编排和 UE5 数据广播均不在本字典和 A 模块实现范围内。
