# V8 运输交接记录设计草案

- 文档状态：已完成开发、独立测试和审计，并冻结为 `backend-db-v8.0.0`
- 依赖基线：`backend-db-v7.0.0`
- 冻结包版本：`8.0.0`
- 范围：A 数据库模块的运输交接事实存储与查询

## 1. 设计结论

V8 只保存一片梁在出场、途中转交或到场接收时已经发生的交接事实。每次交接是一条独立、不可变的记录；录入错误通过作废原记录并新建正确记录处理。

V8 不表达运输计划、派车、运单流程或车辆实时位置，不根据交接结果自动改变梁状态。

## 2. A/B 边界

### 2.1 A 负责

- ORM 模型、Alembic 迁移、DTO、CRUD、Service 和公开 Protocol；
- 项目、梁和平台用户引用校验；
- 交接类型与地点必填性、时间、幂等、作废和项目隔离；
- 页码分页、受控筛选、稳定排序、事务与公开异常。

### 2.2 B 负责

- HTTP、登录态、岗位权限、页面和请求映射；
- 决定何时录入出场、转交或到场事实，以及谁有权作废；
- 运输计划、调度、派车、运单、费用、通知和审批；
- 根据另行确认的业务规则显式调用现有梁状态接口。

### 2.3 明确不开发

- 车辆、司机、承运企业档案及外键；
- GPS、经纬度、轨迹点、电子围栏和设备时序测点；
- 附件、签字、照片、运输单文件和二进制数据；
- 自动改变 `beam.status`、自动追加 V5 事件或自动写入 V3 审计日志；
- 二维码、RFID、一梁一码和通用消息投递。

## 3. 数据模型

新增单表 `beam_transport_handover`，不抽取通用业务记录基表，不增加 JSON 扩展列。

| 字段 | 建议类型 | 可空 | 规则 |
|---|---|---|---|
| `id` | `BIGINT` | 否 | 自增主键 |
| `project_id` | `BIGINT` | 是 | FK→`project.id`，跟随梁；空表示 V1 全局梁 |
| `handover_code` | `VARCHAR(64)` | 否 | 全表唯一、创建后不可修改 |
| `beam_id` | `BIGINT` | 否 | FK→`beam.id` |
| `handover_type` | `VARCHAR(32)` | 否 | `OUTBOUND`、`TRANSFER`、`ARRIVAL` |
| `result_code` | `VARCHAR(32)` | 否 | `ACCEPTED`、`REJECTED` |
| `from_location` | `VARCHAR(255)` | 是 | 起点名称快照 |
| `to_location` | `VARCHAR(255)` | 是 | 终点名称快照 |
| `carrier_name` | `VARCHAR(128)` | 是 | 承运单位快照，不建外键 |
| `vehicle_no` | `VARCHAR(64)` | 是 | 车辆标识快照，不建车辆档案 |
| `sender_name` | `VARCHAR(128)` | 是 | 移交人快照 |
| `receiver_name` | `VARCHAR(128)` | 是 | 接收人快照 |
| `occurred_at` | `DATETIME(6)` | 否 | UTC 交接时间 |
| `actor_user_id` | `BIGINT` | 是 | FK→`app_user.id`，平台记录用户 |
| `actor_name` | `VARCHAR(128)` | 是 | 记录人名称快照 |
| `source` | `VARCHAR(32)` | 否 | 复用 `RecordSource` |
| `external_record_id` | `VARCHAR(128)` | 是 | 外部系统幂等标识 |
| `remark` | `VARCHAR(500)` | 是 | 备注，不保存敏感信息 |
| `is_voided` | `BOOLEAN` | 否 | 默认 false |
| `voided_at` | `DATETIME(6)` | 是 | UTC 作废时间 |
| `voided_by_user_id` | `BIGINT` | 是 | FK→`app_user.id` |
| `voided_by_name` | `VARCHAR(128)` | 是 | 作废人名称快照 |
| `void_reason` | `VARCHAR(500)` | 是 | 作废时必填 |
| `created_at` | `DATETIME(6)` | 否 | A 写入 UTC |
| `updated_at` | `DATETIME(6)` | 否 | 仅受控作废时变化 |

### 3.1 约束

- `handover_code` 唯一；
- `(source, external_record_id)` 唯一，MySQL 允许多行 `NULL`；
- 作废字段使用与 V6、V7 相同的完整性检查约束；
- 外键均使用 `ON DELETE RESTRICT`，不级联删除历史事实；
- 类型和结果使用 Python `StrEnum` 校验，不使用 MySQL ENUM。

## 4. 业务规则

### 4.1 交接类型与地点

- `OUTBOUND`：必须提供 `to_location`，`from_location` 可空；
- `TRANSFER`：`from_location` 和 `to_location` 均必填；
- `ARRIVAL`：必须提供 `from_location`，`to_location` 可空；
- 第一版不禁止起点和终点文本相同，因尚无结构化地点编码可供可靠判断。

### 4.2 交接结果

- `ACCEPTED` 表示当次交接被接收，不等于整个运输任务完成；
- `REJECTED` 表示当次交接未被接收，仍作为独立历史事实保留；
- A 不根据历史记录推断合法路线、先后顺序或当前运输阶段。

### 4.3 项目和梁

- `project_code=None` 只能录入和读取 `project_id IS NULL` 的全局梁记录；
- 项目级梁必须提供匹配的 `project_code`，`project_id` 始终从梁派生；
- 新建项目级记录时项目必须启用；项目后续停用不影响历史读取或完全相同的幂等重试；
- 同一梁允许任意多条交接记录，不额外增加“当前交接”唯一约束。

### 4.4 操作人和交接人

- `actor_user_id` 和 `actor_name` 至少提供一个，表示向系统录入事实的人；
- 提供用户 ID 时必须存在；未提供名称时保存用户当前显示名快照；
- `sender_name` 和 `receiver_name` 是交接双方快照，不与平台用户表强绑定；
- A 不根据用户或人员名称判断岗位和权限。

## 5. 幂等、不可变和作废

### 5.1 幂等

- `handover_code` 全表唯一；
- 提供 `external_record_id` 时，`source + external_record_id` 在运输交接表内唯一；
- 同一幂等标识且全部业务字段相同时返回既有 DTO，不新增记录；
- 编码和外部标识指向不同记录，或同一标识下内容不同时返回 `ResourceConflictError`；
- 并发首次写入使用数据库唯一约束兜底，并在新事务中恢复已有记录；
- 只由 `actor_user_id` 派生的名称快照不因用户后续改名导致幂等冲突。

### 5.2 不可变和作废

- 不提供普通 `update`、物理 `delete` 或恢复接口；
- `void` 锁定主记录，首次写入作废时间、人员和原因；
- 重复或并发作废返回首次结果，不覆盖原作废信息；
- 录入错误时先作废原记录，再使用新 `handover_code` 建立正确事实；
- V8 不增加“替代记录”链，因现有需求未要求直接追踪纠错对应关系。

## 6. DTO 和公开接口

### 6.1 DTO

- `BeamTransportHandoverCreate`：创建交接事实；
- `BeamTransportHandoverVoid`：受控作废命令；
- `BeamTransportHandoverSummary`：列表摘要；
- `BeamTransportHandoverRead`：完整读取 DTO；
- `BeamTransportHandoverFilter`：受控筛选；
- `BeamTransportHandoverSortField`：受控排序枚举；
- `TransportHandoverType`：`OUTBOUND`、`TRANSFER`、`ARRIVAL`；
- `TransportHandoverResult`：`ACCEPTED`、`REJECTED`。

所有 DTO 继承现有 `SchemaModel`，禁止未声明字段，只返回业务编码和快照，不暴露 ORM、Session 或内部外键对象。

### 6.2 B 调用入口

`DatabaseServices` 增加独立的 `transport_records` 入口：

| 方法 | 输入 | 返回 |
|---|---|---|
| `record(data)` | `BeamTransportHandoverCreate` | `BeamTransportHandoverRead` |
| `get(handover_code, project_code=...)` | 业务编码和项目作用域 | `BeamTransportHandoverRead` |
| `list(filters, page_request, sort_by, sort_order)` | Filter、PageRequest、受控排序 | `PageResult[BeamTransportHandoverSummary]` |
| `void(handover_code, data, project_code=...)` | 业务编码、作废 DTO 和项目作用域 | `BeamTransportHandoverRead` |

不增加 HTTP 接口、消息订阅、自动同步或任意字段更新方法。

## 7. CRUD 与 Service 分层

### 7.1 CRUD

CRUD 只负责：

- 创建主记录并 `flush`；
- 按编码、外部幂等键读取；
- 按编码加行锁；
- 白名单筛选、排序和分页；
- 只更新作废字段。

CRUD 不提交事务，不解析项目、不校验业务规则，不返回 DTO。

### 7.2 Service

Service 负责：

- 解析项目、梁和用户；
- 校验项目隔离、启用状态、交接类型和必填地点；
- 处理幂等、并发唯一冲突恢复和作废行锁；
- 管理 Unit of Work、提交或回滚并转换公开异常；
- 将 ORM 转换为 DTO。

不抽取 V6、V7、V8 通用 Service 基类，仅复用已有稳定的项目作用域、Unit of Work、分页和异常转换基础能力。

## 8. 查询、分页和索引

### 8.1 筛选

第一版支持：

- 项目编码、交接编码、梁编码；
- 多个交接类型、多个结果、多个来源；
- `occurred_at_from` 和 `occurred_at_to`；
- `vehicle_no`、`carrier_name`、`actor_user_id`；
- `external_record_id`、`is_voided`；
- 关键词：交接编码、梁编码、地点、车辆、承运单位、交接人、记录人和备注。

空的多值枚举列表表示匹配零条，不解释为“不限”。时间边界统一规范为 UTC 无时区 `datetime`，起始不得晚于结束。

### 8.2 分页和排序

- 复用 `PageRequest` 和 `PageResult`，页大小 1 至 100；
- 默认 `occurred_at DESC, id DESC`；
- 可选排序字段：`id`、`handover_code`、`handover_type`、`result_code`、`occurred_at`、`created_at`；
- 非 ID 排序均追加同方向 `id` 保证稳定分页；
- V8 当前没有明确的增量消费契约，不增加游标接口。

### 8.3 索引

- `(project_id, occurred_at, id)`；
- `(beam_id, occurred_at, id)`；
- `handover_code` 唯一索引；
- `(source, external_record_id)` 唯一索引。

第一版不单独增加车牌、承运单位或关键词索引；待真实数据量和慢查询证明必要后再增加。

## 9. 异常契约

- 新增 `BeamTransportHandoverNotFoundError`，稳定错误码建议为 `beam_transport_handover_not_found`；
- 项目、梁和用户不存在复用已有专用异常；
- 幂等内容冲突、作用域冲突和非法状态复用 `ResourceConflictError`；
- 编码唯一冲突在无可恢复记录时返回 `ResourceAlreadyExistsError`；
- 不将 SQLAlchemy、PyMySQL、ORM 实例或数据库索引名暴露给 B。

## 10. 测试和审计要求

### 10.1 功能与契约

1. 三种交接类型的合法和缺失地点组合；
2. `ACCEPTED`、`REJECTED` 均能作为事实保存；
3. 项目梁、全局梁、错误项目和停用项目；
4. 用户名称快照及外部人员名称；
5. 编码幂等、外部幂等、不同内容冲突和两键分裂冲突；
6. 首次并发创建只保留一条；
7. 作废、重复作废、并发作废和字段不可覆盖；
8. 筛选、关键词、时间范围、分页、无总数分页和稳定排序；
9. 记录创建和作废不改变梁状态，不新增 V5 事件或 V3 审计日志；
10. DTO、Protocol、组合工厂和 wheel 公开导入。

### 10.2 数据库和回归

- 开发库和 `_test` 库的升级、降级、重新升级和 `alembic check`；
- 字段、外键、唯一约束、检查约束和索引与数据字典一致；
- flush 后 DTO 转换失败时整个创建事务回滚；
- V1 至 V7 完整回归；
- 并发用例重复运行，无死锁、超时和偶发失败；
- 测试数据和构建临时文件清理完成。

## 11. 最小开发顺序

1. 确认本设计中的交接类型、结果、地点必填性和不联动梁状态；
2. 新增 Schema 和枚举测试；
3. 新增单表 ORM 与一份向前 Alembic 迁移；
4. 新增专用 CRUD 和 Service，不抽取通用记录基类；
5. 接入 `transport_records` Protocol 和组合工厂；
6. 完成幂等、并发、作废、查询和事务测试；
7. 更新 README、数据字典、A-B 接入说明及测试/审计交接文档；
8. 完整回归、迁移往返、并发、wheel 和残留数据验证后，再交给独立测试与审计。

## 12. 已确认的开发决策

用户授权开始 V8 开发后，本版本按以下默认决策实现：

1. 类型只使用 `OUTBOUND`、`TRANSFER`、`ARRIVAL`；
2. 结果只使用 `ACCEPTED`、`REJECTED`；
3. 地点必填性按第 4.1 节执行，不要求地点编码或地点表外键；
4. 交接双方、车辆和承运单位只保存文本快照；
5. 交接记录不自动修改梁状态或生命周期事件；
6. 第一版不提供游标增量查询。

后续正式需求若改变上述口径，通过新版本和向前迁移调整，不静默改写已有数据含义。
