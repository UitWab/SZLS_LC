## 一 任务目标

本任务对 A 负责的 `backend_db` 数据库模块 V2 进行独立、只读审计，重点发现设计错误、数据完整性风险、安全边界问题、迁移风险、接口耦合、测试盲区和文档不一致。

审计任务不执行修复，不修改代码或文档，不生成迁移，不提交、不推送。允许执行只读检查和不会改变开发库的测试；数据库降级等状态变更交由专门测试任务完成。

## 四 审计范围边界

A 的允许范围：

- MySQL 表结构、约束和索引；
- SQLAlchemy ORM；
- Alembic 迁移；
- CRUD 数据访问；
- Service 事务和数据规则；
- Pydantic DTO、筛选、分页、排序和异常；
- 供 B 调用的 Python Protocol 与组合工厂；
- 数据字典和 A→B 数据契约；
- 自动化测试。

A 不得实现：

- FastAPI 路由和 HTTP 响应；
- 密码明文处理和具体散列算法；
- JWT、Cookie、Session 登录态和鉴权中间件；
- Redis、MQTT、WebSocket；
- 前端、UE5 或 PLC 模拟器；
- 页面、菜单和岗位展示逻辑；
- 生产工序流转和任务编排。

发现越界实现必须单独列为范围缺陷。

## 五 审计方法

### 1 工作区与变更完整性

- 确认分支和完整提交号。
- 枚举所有修改文件和未跟踪文件。
- 以 V1 提交和标签为基线审查 V2 增量。
- 确认没有临时脚本、构建产物、数据库密码、缓存或测试文件残留。
- 禁止使用会改写工作区的 Git 命令。

### 2 架构和依赖方向

检查依赖是否保持：

```text
interfaces → services → crud → models/database
                 ↓
              schemas
```

重点确认：

- B 只需导入 `backend_db.interfaces`、`backend_db.schemas` 和公开异常；
- Protocol 不导入 ORM、Session 或 SQLAlchemy 查询对象；
- Service 不向外返回 ORM；
- CRUD 不混入 HTTP、认证会话或页面规则；
- 每个 Service 调用拥有明确 Unit of Work 边界；
- 工厂采用延迟导入，没有不必要的初始化副作用；
- 新功能没有大幅重构 V1 代码。

### 3 数据模型和完整性

逐表审查：

- `project`
- `process_definition`
- `app_user`
- `user_credential`
- `auth_role`
- `auth_permission`
- `auth_role_permission`
- `auth_user_role`
- `project_member`
- `project_member_role`
- V1 的 `yard_area`、`beam_type`、`beam_position`、`beam`

重点问题：

- 主键、外键、唯一约束、非空性和索引是否与查询场景匹配；
- 所有核心外键是否保持 `RESTRICT`，是否存在意外级联删除；
- `project_id` 可空过渡策略是否安全且文档一致；
- 工序编码采用全局唯一是否与当前单项目过渡策略一致；
- 工序 `sort_order` 是否被错误解释为强制业务流程；
- 用户和密码凭据是否真正隔离；
- 系统角色和项目角色能否被错误交叉分配；
- 项目成员联合唯一是否可靠；
- 停用资源是否仍会错误参与有效权限计算；
- 权限合并是否去重、稳定排序且不存在跨项目泄漏；
- 是否存在 ORM 关系、懒加载或 Session 生命周期问题。

### 4 安全审计

重点检查：

- 普通 `UserRead` 和用户列表绝不包含 `password_hash`；
- 明文 `password` 输入被 DTO 拒绝；
- `UserAuthRecord` 是否被明确隔离，是否存在误用风险；
- 密码散列长度和更新时间是否合理；
- 排序字段是否通过枚举白名单，不能注入任意数据库列；
- 筛选关键字是否使用安全表达式；
- 错误信息是否泄漏数据库连接或敏感数据；
- 停用用户、角色、权限、项目和成员的授权语义是否一致；
- 撤权是否幂等，失败事务是否回滚；
- 是否存在默认管理员、默认密码或种子权限数据。

### 5 CRUD 和 Service 语义

逐个公开方法核对：

- 创建、读取、列表、部分更新和启停是否闭环；
- 稳定业务编码是否禁止被更新；
- 分页边界为页码大于等于 1、每页 1 到 100；
- `include_total=False` 时是否使用多取一条判断下一页；
- 非主键排序是否追加主键形成稳定顺序；
- 关联资源不存在、停用、重复或范围错误时是否转换为稳定公开异常；
- 分配和撤销是否幂等；
- 所有写操作是否在返回前提交，异常时是否回滚；
- 是否存在先构造 DTO、后刷新导致返回旧值的问题；
- 是否意外提供任何物理删除用户、角色、项目、工序或梁的接口。

### 6 迁移审计

按顺序审查：

1. `a006ca44c863`
2. `b7f3c92e1a64`
3. `c9d4e6f1a2b8`
4. `d2a8f41c6e90`
5. `e5c1a7b3d902`

确认：

- `down_revision` 形成单一连续链；
- 升级顺序满足外键依赖；
- 降级按子表到父表顺序执行；
- MySQL 非事务 DDL 失败时是否存在部分迁移风险；
- ORM 和迁移的字段类型、长度、空值、默认值、注释、索引和约束一致；
- 未创建虚假默认项目，也未擅自回填存量数据；
- `alembic check` 能检测为无待生成变更。

审计任务可以执行 `alembic current` 和 `alembic check`，但不得对开发库执行 upgrade、downgrade 或手工 SQL。

### 7 契约和文档一致性

逐项对照代码、README、A→B 接入说明、Markdown 字典和 XLSX 字典：

- 包版本是否均为 `2.0.0`；
- 数据契约版本是否为 `2.0.0`；
- 最新迁移是否均为 `e5c1a7b3d902`；
- 表名、字段、可空性、唯一约束和外键是否一致；
- Service 属性和方法是否完整；
- B 的允许与禁止依赖是否清楚；
- 密码散列职责是否明确归属于 B；
- 工序基础资料与工序流转边界是否明确；
- V1 不删除梁、14 个状态可演进的规则是否保持。

### 8 测试充分性

审计已有测试是否覆盖：

- 正常路径、异常路径和幂等行为；
- 密码散列泄漏防护；
- 角色范围错误；
- 停用资源的有效权限；
- 跨项目权限隔离；
- 分页、筛选和稳定排序；
- 事务回滚；
- 迁移结构与降级；
- V1 回归；
- 公开 Protocol 类型注解可解析；
- 无物理删除接口。

测试通过不代表审计通过。未覆盖但高风险的路径应作为测试缺口报告。

## 六 严重级别

- P0：可能造成开发库或生产数据破坏、敏感凭据泄漏、完全绕过授权，必须立即阻止交付。
- P1：核心数据完整性、跨项目隔离、迁移或公开契约存在重大错误，V2 不应冻结。
- P2：特定条件下行为错误、维护风险明显或测试存在重要盲区，建议冻结前修复。
- P3：低风险一致性、可读性或文档问题，可排入后续维护。

不要为了填充报告而制造问题。没有发现问题时，应明确说明审查过的范围和仍然存在的验证限制。

## 七 审计报告格式

报告必须以发现项为首，不先写过程总结。每个发现项包含：

1. 严重级别和简短标题；
2. 具体文件及准确行号；
3. 触发条件或复现方式；
4. 实际影响；
5. 为什么现有约束或测试没有阻止；
6. 最小修复建议，但不实施修复。

发现项之后再给出：

- 已审查范围；
- 未审查或无法验证的范围；
- A/B 边界结论；
- 数据迁移结论；
- 安全结论；
- 文档一致性结论；
- 是否建议冻结 V2。

如果没有 P0 到 P2 问题，应写明“未发现阻止冻结的问题”，但仍列出剩余风险和测试盲区。不得只回复“代码没有问题”。
