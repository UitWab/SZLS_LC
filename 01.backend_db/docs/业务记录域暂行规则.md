# 智能建梁数字孪生平台业务记录域暂行规则

- 文档状态：暂行规则草案，尚未形成稳定对外契约
- 适用范围：梁工序执行、质量检查、运输交接、设备告警
- 排除范围：设备时序测点

## 1. 文档目的

本文定义梁工序执行、质量检查、运输交接和设备告警四类记录的第一版暂行规则，作为后续数据库设计、接口设计、测试和审计的共同依据。规则允许在获得真实业务资料后通过新版本和 Alembic 迁移扩展，但不得直接改变已经保存的数据含义。

本文不代表四类记录已经开发完成。每类记录必须按独立版本完成设计复核、编码、测试、审计和冻结后，才能作为稳定契约交付 B。

设备时序测点明确不在本文范围内。二维码、RFID、生产排程、审批流、文件存储、消息通知、设备通信和页面也不进入本次记录域。

## 2. 总体边界

### 2.1 A 模块负责

- ORM 模型和 Alembic 迁移；
- Pydantic DTO、CRUD、Service 和公开 Python Protocol；
- 项目、梁、工序和用户引用校验；
- 唯一性、项目隔离、受控作废、事务和并发约束；
- 页码分页、条件筛选、稳定排序和公共异常；
- 自动测试、数据字典、A-B 接入说明和审计资料。

### 2.2 B 模块负责

- HTTP、登录态、岗位权限和页面；
- 决定何时创建记录、谁可以提交、作废、确认或关闭；
- 生产流程编排、质量审批、运输调度和告警通知；
- 密码、JWT、请求体、文件上传和文件存储；
- 设备协议、网关、采集、重试和消息队列；
- 根据业务规则决定是否调用现有梁状态修改接口。

### 2.3 明确不建设通用记录表

四类记录分别建模，不创建同时容纳工序、质量、运输和告警的万能 `business_record` 表，也不创建不受约束的大型 JSON 载荷。不同记录的生命周期、数据量、查询条件和修正规则不同，强行共表会降低约束能力并增加长期耦合。

## 3. 共同数据规则

1. 每条记录使用数据库自增 `id` 作为内部关联键，同时使用最长 64 字符的稳定业务编码作为跨模块标识。
2. 业务编码创建后不可修改，并在对应记录表内唯一。
3. 记录必须关联梁；`project_id` 跟随梁。为兼容当前 V1 全局梁，第一版允许为空，但项目级梁的记录必须与梁属于同一项目。
4. 对外 DTO 返回 `project_code`、`beam_code`、`process_code` 等业务编码，不返回 ORM 对象或数据库 Session。
5. 类型、状态、结果和来源使用 `VARCHAR` 与 Python `StrEnum`，不使用 MySQL ENUM。已有代码含义不得复用或改写，只能新增或废弃。
6. 记录创建后不提供任意更新和物理删除。确需纠错时，只允许受控作废，并另外创建正确记录。
7. 作废保留原始内容，并保存 `voided_at`、可空 `voided_by_user_id`、`voided_by_name` 和必填 `void_reason`。已作废记录不能恢复或再次作废。
8. 每类记录使用含义明确的业务时间字段：工序执行使用 `started_at`、`finished_at`，质量检查使用 `inspected_at`，运输交接和设备告警使用 `occurred_at`。这些时间由 B 提供 UTC 时间；`created_at` 由 A 写入 UTC 时间。不得以 `created_at` 冒充业务时间。
9. 可空 `actor_user_id` 关联平台用户，可空 `actor_name`保存操作人快照。提供用户 ID 时 A 必须验证用户存在；没有平台账号的外部人员只保存名称快照。
10. `source` 第一版允许 `MANUAL`、`SYSTEM`、`IMPORT`、`DEVICE`。A 校验代码，B 决定真实来源。
11. 外部系统或设备重试写入时使用 `external_record_id`。提供该值时，`source + external_record_id` 在同类记录中唯一；重复请求返回既有记录，不重复写入。
12. 备注和摘要不得保存密码、令牌、完整请求报文、设备密钥或其他敏感信息。
13. 文件和照片由 B 或独立文件服务保存。A 第一版不保存二进制文件，也不在没有文件服务契约时保存临时本地路径。
14. 业务记录不自动写入 V3 操作审计日志。B 在操作完成后显式调用 `audit_logs.record`。
15. 业务记录不自动修改 `beam.status`，也不自动追加新的 V5 生命周期事件类型。若以后确认联动规则，必须单独设计事务、失败回滚和并发顺序。
16. 普通查询使用页码分页和稳定的 `sort_field + id` 次级排序。只有出现明确的数字孪生增量消费需求时，才为相应记录单独设计游标。

## 4. 梁工序执行记录

### 4.1 记录含义

一条梁工序执行记录表示一片梁在某一道已配置工序上的一次实际执行结果。它不是生产计划、待办任务或审批单，不表达未来安排。

同一片梁可以多次执行同一工序，用于返工、复做或不同批次执行。每次执行必须使用新的 `execution_code`，不覆盖之前记录。

### 4.2 暂行字段

| 字段 | 规则 |
|---|---|
| `execution_code` | 稳定业务编码，唯一，不可修改 |
| `project_id` | 跟随梁项目 |
| `beam_id` | 必填，关联梁 |
| `process_definition_id` | 必填，关联启用的项目工序或平台通用工序 |
| `result_code` | `SUCCESS`、`FAILED`、`ABORTED` |
| `started_at` | 必填，UTC |
| `finished_at` | 必填，UTC，不得早于开始时间 |
| `actor_user_id` | 可空平台用户 |
| `actor_name` | 可空操作人快照 |
| `source` | 记录来源 |
| `external_record_id` | 可空外部幂等标识 |
| `remark` | 可空，最长 500 字符 |
| 作废字段 | 按共同规则保存 |
| `created_at` | A 写入 UTC |

### 4.3 业务规则

- 三种结果均必须提供 `finished_at`；工序执行记录只表达已经结束的事实。
- 工序与梁必须属于同一项目，平台通用工序可以用于项目梁。
- 停用工序不能用于新记录，但历史记录仍可查询。
- 同一梁同一工序允许存在多条成功或失败记录，A 不推断返工原因和工序顺序。
- 不根据工序记录自动判断下一工序，也不自动修改梁状态。

### 4.4 建议公开接口

- `process_records.record(data)`；
- `process_records.get(execution_code, project_code=...)`；
- `process_records.list(filters, page_request, sort_by, sort_order)`；
- `process_records.void(execution_code, data, project_code=...)`。

筛选至少支持项目、梁、工序、多个结果、来源、发生时间范围、是否作废和关键词。

## 5. 质量检查记录

### 5.1 记录含义

一条质量检查记录表示对一片梁进行的一次独立检查或验收。它保存检查结论和可选检查项，不承担审批流程、电子签章或质量文件存储。

复检必须创建新记录，并通过 `previous_inspection_id` 指向被复检记录；不得覆盖原检查结果。

### 5.2 主记录暂行字段

| 字段 | 规则 |
|---|---|
| `inspection_code` | 稳定业务编码，唯一，不可修改 |
| `project_id` | 跟随梁项目 |
| `beam_id` | 必填，关联梁 |
| `process_definition_id` | 可空，表示关联工序 |
| `process_execution_id` | 可空，表示关联某次工序执行；提供时梁、项目和工序必须一致 |
| `previous_inspection_id` | 可空，复检时指向同一梁的既有检查记录 |
| `inspection_type_code` | 由双方维护的稳定检查类型代码 |
| `result_code` | `PASS`、`FAIL` |
| `inspected_at` | 必填，UTC |
| `actor_user_id` | 可空检查用户 |
| `actor_name` | 可空检查人快照 |
| `source` | 记录来源 |
| `external_record_id` | 可空外部幂等标识 |
| `summary` | 可空结论摘要，最长 500 字符 |
| 作废字段 | 按共同规则保存 |
| `created_at` | A 写入 UTC |

### 5.3 检查项暂行字段

质量检查项作为主记录的子表，与主记录在同一事务中一次性创建：

| 字段 | 规则 |
|---|---|
| `inspection_id` | 必填，关联质量检查主记录 |
| `item_code` | 本次检查中的稳定项目代码 |
| `item_name` | 检查项目名称快照 |
| `requirement_text` | 可空验收要求快照 |
| `observed_value` | 可空实际值文本，最长 128 字符 |
| `unit` | 可空单位，最长 32 字符 |
| `result_code` | `PASS`、`FAIL`、`NOT_APPLICABLE` |
| `remark` | 可空说明 |

主记录与检查项一旦创建均不任意更新。第一版不为不同检查类型预建大量专用字段；待真实模板稳定后，再把需要范围查询或数值计算的检查项迁移为专用结构。

### 5.4 业务规则

- 至少存在一个检查项时，只要任一适用检查项为 `FAIL`，主记录不得为 `PASS`。
- `previous_inspection_id` 必须属于同一项目、同一梁，且不能指向自身或形成循环。
- 关联工序执行时，检查记录的工序必须与执行记录一致；未直接提供工序时可以从执行记录确定。
- A 不决定不合格后的返工、审批、放行或梁状态变化。
- 第一版不提供检查记录任意修改、物理删除、附件上传或电子签章。

### 5.5 建议公开接口

- `quality_records.record(data)`；
- `quality_records.get(inspection_code, project_code=...)`；
- `quality_records.list(filters, page_request, sort_by, sort_order)`；
- `quality_records.void(inspection_code, data, project_code=...)`。

筛选至少支持项目、梁、工序、检查类型、多个结果、是否复检、检查时间范围、是否作废和关键词。

## 6. 运输交接记录

### 6.1 记录含义

一条运输交接记录表示一片梁在出场、途中转交或到场接收时的一次交接事实。它不是运输计划、调度任务、车辆实时定位或轨迹点。

### 6.2 暂行字段

| 字段 | 规则 |
|---|---|
| `handover_code` | 稳定业务编码，唯一，不可修改 |
| `project_id` | 跟随梁项目 |
| `beam_id` | 必填，关联梁 |
| `handover_type` | `OUTBOUND`、`TRANSFER`、`ARRIVAL` |
| `result_code` | `ACCEPTED`、`REJECTED` |
| `from_location` | 可空地点名称快照 |
| `to_location` | 可空地点名称快照 |
| `carrier_name` | 可空承运单位快照 |
| `vehicle_no` | 可空车辆标识，不关联设备表 |
| `sender_name` | 可空移交人快照 |
| `receiver_name` | 可空接收人快照 |
| `occurred_at` | 必填交接时间，UTC |
| `actor_user_id` | 可空平台记录用户 |
| `actor_name` | 可空记录人快照 |
| `source` | 记录来源 |
| `external_record_id` | 可空外部幂等标识 |
| `remark` | 可空，最长 500 字符 |
| 作废字段 | 按共同规则保存 |
| `created_at` | A 写入 UTC |

### 6.3 业务规则

- `OUTBOUND` 必须提供 `to_location`，`ARRIVAL` 必须提供 `from_location`，`TRANSFER` 必须同时提供两者。
- `ACCEPTED` 表示本次交接被接收，不等价于运输任务完成；`REJECTED` 保留失败交接事实。
- A 不校验运输路线先后，不阻止同一梁出现多次交接，也不自动修改 `TRANSPORTING`、`ARRIVED` 等梁状态。
- 车辆标识、承运单位和人员名称采用事实快照，第一版不建设车辆、司机和运输企业档案。
- 第一版不保存经纬度、轨迹、电子围栏、运单费用或车辆时序数据。

### 6.4 建议公开接口

- `transport_records.record(data)`；
- `transport_records.get(handover_code, project_code=...)`；
- `transport_records.list(filters, page_request, sort_by, sort_order)`；
- `transport_records.void(handover_code, data, project_code=...)`。

筛选至少支持项目、梁、交接类型、多个结果、车辆标识、承运单位、发生时间范围、是否作废和关键词。

## 7. 设备告警记录

### 7.1 记录含义

设备告警记录保存外部设备或系统已经产生的告警及其受控处理状态。A 不判断采集值是否应触发告警，不连接设备，也不保存设备时序测点。

第一版尚无设备档案表，因此使用 `device_code` 字符串保存外部稳定设备标识，不建立不存在的设备外键。以后设备档案需求明确后，再评估迁移关联。

### 7.2 暂行字段

| 字段 | 规则 |
|---|---|
| `alarm_code` | A/B 使用的稳定告警业务编码，唯一 |
| `project_id` | 必填，关联项目；设备告警不创建全局记录 |
| `beam_id` | 可空；只有告警明确关联梁时填写且必须属于同一项目 |
| `device_code` | 必填外部设备稳定标识 |
| `alarm_type_code` | 必填稳定告警类型代码 |
| `severity` | `INFO`、`WARNING`、`CRITICAL` |
| `status` | `ACTIVE`、`ACKNOWLEDGED`、`RECOVERED`、`CLOSED` |
| `message` | 必填告警摘要，最长 500 字符，不保存完整原始报文 |
| `occurred_at` | 必填告警发生时间，UTC |
| `acknowledged_at` | 可空确认时间 |
| `acknowledged_by_user_id` | 可空确认用户 |
| `acknowledged_by_name` | 可空确认人快照 |
| `recovered_at` | 可空恢复时间 |
| `closed_at` | 可空关闭时间 |
| `source` | 固定为 `DEVICE` 或 `SYSTEM` |
| `external_record_id` | 必填，承担设备或外部系统重试幂等 |
| `created_at`、`updated_at` | A 写入 UTC |

### 7.3 状态规则

允许的受控状态变化：

- `ACTIVE -> ACKNOWLEDGED`；
- `ACTIVE -> RECOVERED`；
- `ACKNOWLEDGED -> RECOVERED`；
- `ACTIVE -> CLOSED`；
- `ACKNOWLEDGED -> CLOSED`；
- `RECOVERED -> CLOSED`。

重复确认、恢复或关闭按幂等成功处理。关闭后不重新打开；外部系统再次报告同一故障时必须使用新的告警业务编码或新的外部记录标识。

确认只表示人员已知晓，恢复表示告警条件已经消失，关闭表示业务处理结束。三者不得混用。

### 7.4 建议公开接口

- `device_alarms.record(data)`：接收新告警，按外部标识幂等；
- `device_alarms.get(alarm_code, project_code=...)`；
- `device_alarms.list(filters, page_request, sort_by, sort_order)`；
- `device_alarms.acknowledge(alarm_code, data, project_code=...)`；
- `device_alarms.recover(alarm_code, data, project_code=...)`；
- `device_alarms.close(alarm_code, data, project_code=...)`。

筛选至少支持项目、梁、设备、告警类型、多个等级、多个状态、发生时间范围和关键词。

设备告警不提供普通更新、物理删除或任意状态赋值接口。

## 8. 查询、索引和性能原则

- 第一版所有管理查询均使用 `PageRequest` 和 `PageResult`，页大小继续限制在 1 到 100。
- 默认按业务发生时间倒序，并使用 `id DESC` 保证相同时间下顺序稳定。
- 每张表至少为项目加业务时间建立组合索引，为梁加业务时间建立组合索引。
- 工序执行和质量检查按 `process_definition_id` 的实际查询增加组合索引。
- 运输交接按车辆查询只有出现明确使用量后才增加专用索引。
- 设备告警需要 `(project_id, status, occurred_at, id)` 和 `(project_id, device_code, occurred_at, id)` 索引。
- 不提前为每个可筛选字段建立索引；索引必须由查询路径和数据量证明。

## 9. 异常和安全原则

每类记录提供自己的不存在异常，同时复用现有公共异常父类。项目范围错误统一表现为记录不存在，不向调用方泄露其他项目数据是否存在。

唯一编码冲突、外部幂等冲突、非法状态变化、作废后重复操作、跨项目引用、停用工序引用和时间范围错误必须转换为稳定公开异常，不向 B 暴露 SQLAlchemy 或 PyMySQL 异常。

备注、摘要、地点、车辆和人员快照都按长度限制处理。A 不拼接原生 SQL，不允许调用方指定任意排序列，也不返回内部外键关系对象。

## 10. 暂行规则的变更方式

1. 新增字段优先采用可空字段或独立子表，并通过 Alembic 向前迁移。
2. 已有字段代码和含义不得静默修改；需要替换时新增字段或代码，并提供迁移说明。
3. 暂行枚举允许新增值；废弃值继续支持历史读取，不再允许新建。
4. 详细检查模板、设备档案或运输任务明确后，以独立领域扩展，不把现有记录表改成通用工作流。
5. 每次契约变化同步更新 Schema、Protocol、A-B 接入说明、数据字典、测试和版本说明。

## 11. 开发前仍需逐项确认

本文已经给出可以编码的默认规则，但每一版本开始前仍应复核以下最小问题：

- 该类记录是否确实需要进入当前交付范围；
- 暂行类型和结果代码是否满足演示及联调；
- 操作人使用用户 ID、名称快照或两者并存是否符合来源系统；
- B 是否需要外部幂等标识；
- 是否存在必须参与筛选或统计的专用字段；
- 是否需要与梁状态联动。默认答案始终为“不自动联动”。

未确认的问题使用本文默认规则，不扩大范围；若默认规则与新资料冲突，应先修订设计，不带冲突进入编码。
