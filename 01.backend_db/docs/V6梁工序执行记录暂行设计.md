# 智能建梁数字孪生平台数据库 V6 梁工序执行记录暂行设计

- 文档状态：已按暂行规则完成开发并本地冻结
- 计划版本：V6.0
- 冻结标签：`backend-db-v6.0.0`
- 依赖基线：随同一 6.0.0 基线冻结的 V5 梁生命周期事件实现
- 目标数据库：MySQL 8.0

## 1. 目标

V6 为一片梁在某一道已配置工序上的一次实际执行保存稳定记录，为后续生产履历查询和 V7 质量检查提供可选关联基础。

一条工序执行记录表示一次已经结束并产生结果的执行事实。它不是生产计划、待办任务、派工单、审批单或进行中状态，不负责安排下一工序。

## 2. 范围

### 2.1 V6 实现

- 梁工序执行记录的数据模型和迁移；
- 创建、单条读取、分页筛选和受控作废；
- 项目、梁、工序和操作用户引用校验；
- 外部来源幂等；
- DTO、Service、公开 Python Protocol 和组合工厂入口；
- 测试、数据字典和 A-B 接入文档。

### 2.2 V6 不实现

- 生产计划、工序排程、派工和审批；
- 进行中任务、暂停、恢复和进度百分比；
- 工序先后顺序、前置条件和状态机；
- 自动修改 `beam.status`；
- 自动新增 V5 生命周期事件；
- 质量检查项、附件、电子签章；
- HTTP、登录鉴权、页面、通知和消息队列；
- 设备接入、设备时序测点和设备控制。

## 3. 核心定义

### 3.1 一条记录代表什么

一条 `beam_process_execution` 记录表示：某一片梁在某一道工序上，从 `started_at` 到 `finished_at` 完成的一次实际执行，其结果为成功、失败或中止。

记录必须在本次执行已经结束后创建。若 B 需要表达“计划中”或“执行中”，应另行设计生产任务，不使用 V6 记录模拟任务状态。

### 3.2 重复执行

同一片梁允许多次执行同一道工序。返工、复做、失败后重试或不同批次执行均创建新记录，不覆盖历史记录，也不限制成功记录数量。

A 不根据 `process_definition.sort_order` 判断工序执行是否合法，不阻止跳序或重复执行。顺序和放行规则属于 B 的生产流程职责。

### 3.3 记录修正

业务字段创建后不可任意修改。错误记录先通过受控接口作废，再创建新的正确记录。新记录可以通过 `supersedes_execution_id` 指向被替代记录，形成可追溯的修正关系。

作废不删除原记录，不清除原结果、时间、操作人或来源信息。已作废记录不能恢复或再次作废。

## 4. 数据模型

计划表名：`beam_process_execution`。

| 字段 | 类型 | 可空 | 规则 |
|---|---|---|---|
| `id` | `BIGINT` | 否 | 自增主键，仅用于内部关联 |
| `project_id` | `BIGINT` | 是 | 跟随梁项目；兼容当前全局梁 |
| `execution_code` | `VARCHAR(64)` | 否 | 稳定业务编码，全表唯一，创建后不可修改 |
| `beam_id` | `BIGINT` | 否 | 关联 `beam.id`，删除限制 `RESTRICT` |
| `process_definition_id` | `BIGINT` | 否 | 关联 `process_definition.id`，删除限制 `RESTRICT` |
| `result_code` | `VARCHAR(32)` | 否 | `SUCCESS`、`FAILED`、`ABORTED` |
| `started_at` | `DATETIME(6)` | 否 | 实际开始时间，UTC |
| `finished_at` | `DATETIME(6)` | 否 | 实际结束时间，UTC，不得早于开始时间 |
| `actor_user_id` | `BIGINT` | 是 | 可空平台操作用户，删除限制 `RESTRICT` |
| `actor_name` | `VARCHAR(128)` | 是 | 操作人名称或标识快照 |
| `source` | `VARCHAR(32)` | 否 | `MANUAL`、`SYSTEM`、`IMPORT`、`DEVICE` |
| `external_record_id` | `VARCHAR(128)` | 是 | 外部来源幂等标识 |
| `supersedes_execution_id` | `BIGINT` | 是 | 可空自关联，指向被替代的已作废记录 |
| `remark` | `VARCHAR(500)` | 是 | 不含敏感信息的执行说明 |
| `is_voided` | `BOOLEAN` | 否 | 默认 `FALSE`，仅由受控作废接口修改 |
| `voided_at` | `DATETIME(6)` | 是 | 作废时间，UTC |
| `voided_by_user_id` | `BIGINT` | 是 | 可空作废用户，删除限制 `RESTRICT` |
| `voided_by_name` | `VARCHAR(128)` | 是 | 作废人名称或标识快照 |
| `void_reason` | `VARCHAR(500)` | 是 | 作废时必填 |
| `created_at` | `DATETIME(6)` | 否 | A 写入 UTC |
| `updated_at` | `DATETIME(6)` | 否 | A 写入 UTC；正常只在作废时变化 |

## 5. 字段和引用规则

### 5.1 项目与梁

- `project_id` 必须等于梁的 `project_id`。
- 停用项目不能创建新的执行记录，已有历史记录仍可查询和作废。
- B 使用 `project_code` 和 `beam_code` 调用，不直接提交内部 ID。
- `project_code=None` 只允许访问当前兼容 V1 的全局梁及其记录。
- 提供项目编码时，只能访问该项目记录；跨项目读取统一表现为记录不存在。

### 5.2 工序

- 项目梁可以使用同项目启用工序，也可以使用启用的平台通用工序。
- 全局梁只能使用平台通用工序。
- 工序一旦被执行记录引用，其项目归属不可再修改；名称、排序、备注和启停状态仍可维护。需要调整项目归属时应新建工序并保留原工序。
- 停用工序不能用于创建新执行记录，但停用前的历史执行记录仍可读取。
- 工序名称和排序变化不修改历史执行记录；历史展示默认读取当前工序基础资料。
- 第一版不保存工序名称快照。若未来要求严格还原当时显示名称，再通过迁移增加快照字段。

### 5.3 操作人

- `actor_user_id` 和 `actor_name` 至少提供一个。
- 提供用户 ID 时，用户必须存在；未提供名称时，A 使用当前用户显示名称写入快照。
- 外部人员没有平台用户时，可以只提供 `actor_name`。
- A 不判断该用户是否有权执行工序，权限由 B 在调用前处理。

### 5.4 时间

- `started_at` 和 `finished_at` 均由 B 提供，必须是 UTC 业务时间。
- `finished_at >= started_at`。
- A 不以当前数据库时间替代缺失的业务开始或结束时间。
- 执行时长由查询方根据两个时间计算，第一版不重复保存 `duration`。

### 5.5 结果

- `SUCCESS`：工序本次执行成功结束。
- `FAILED`：工序本次执行结束但未达到成功条件。
- `ABORTED`：工序在完成前被中止，但本次执行事实已经结束。
- 结果不等价于质量验收结论。质量是否通过由 V7 质量检查记录表达。

## 6. 幂等规则

### 6.1 业务编码

`execution_code` 全表唯一。不同项目也不能复用同一执行编码，避免跨模块路由和日志中产生歧义。

### 6.2 外部记录标识

`external_record_id` 对人工录入可空，对 `SYSTEM`、`IMPORT`、`DEVICE` 来源建议必填。提供后，`source + external_record_id` 在工序执行表内唯一。

重复调用规则：

1. 相同来源和外部标识、且业务内容一致时，返回既有记录，不重复插入。
2. 相同来源和外部标识、但梁、工序、时间或结果不同，返回稳定冲突异常，不静默覆盖。
3. 相同 `execution_code` 且内容一致，也可按幂等成功返回；内容不同则返回编码冲突。
4. 并发重复请求以数据库唯一约束作为最终保护，Service 将唯一约束异常转换为公共异常。

外部幂等键只解决重复提交，不承担消息确认、消费位点或 exactly-once 投递语义。

## 7. 修正和作废规则

### 7.1 作废条件

- 只有未作废记录可以执行作废。
- 作废必须提供原因，并至少提供作废用户或作废人名称。
- 作废接口只修改作废相关字段和 `updated_at`，不得同时修改执行结果、时间、梁或工序。
- 重复作废返回当前记录，按幂等成功处理；不得覆盖第一次作废人、原因和时间。

### 7.2 替代记录

- `supersedes_execution_id` 只能指向同项目、同一梁、同一道工序的记录。
- 被替代记录必须已经作废。
- 新记录不能指向自身，也不能形成替代循环。
- 第一版允许一个作废记录只被一条新记录直接替代，以唯一约束避免修正关系分叉。
- 替代关系只表达纠错，不表达返工。正常返工记录不填写该字段。

## 8. 数据库约束和索引

### 8.1 约束

- 主键：`id`；
- 唯一：`execution_code`；
- 唯一：`(source, external_record_id)`，外部标识为空时不参与冲突；
- 唯一：`supersedes_execution_id`，为空时允许多条普通记录；
- 外键：项目、梁、工序、操作用户、作废用户和自关联记录均使用 `RESTRICT`；
- 检查：`finished_at >= started_at`；
- 检查：未作废时作废字段为空；作废时 `voided_at` 和 `void_reason` 非空。

项目一致性、工序启用状态、操作人至少一个以及替代关系范围由 Service 校验；数据库外键和唯一约束作为最终保护。

### 8.2 第一版索引

- `(project_id, finished_at, id)`：项目执行历史和默认排序；
- `(beam_id, finished_at, id)`：单梁生产履历；
- `(process_definition_id, finished_at, id)`：工序执行历史；
- 唯一约束对应索引不重复创建。

第一版不为结果、来源和作废状态分别建立单列索引。真实数据量和慢查询证明需要后再增加。

## 9. DTO 设计

### 9.1 枚举

- `BeamProcessResult`：`SUCCESS`、`FAILED`、`ABORTED`；
- `RecordSource`：`MANUAL`、`SYSTEM`、`IMPORT`、`DEVICE`；
- `BeamProcessExecutionSortField`：`ID`、`EXECUTION_CODE`、`RESULT_CODE`、`STARTED_AT`、`FINISHED_AT`、`CREATED_AT`。

`RecordSource` 后续可被其他记录域复用，但只放在 Schema 枚举层，不建立通用 ORM 基类或通用 Service。

### 9.2 输入 DTO

- `BeamProcessExecutionCreate`：项目、执行编码、梁、工序、结果、时间、操作人、来源、外部标识、可选替代记录和备注；
- `BeamProcessExecutionVoid`：作废用户、作废人名称和原因；
- `BeamProcessExecutionFilter`：查询条件。

### 9.3 输出 DTO

- `BeamProcessExecutionSummary`：列表所需稳定字段；
- `BeamProcessExecutionRead`：完整详情和作废信息；
- 使用既有 `PageRequest` 和 `PageResult`。

所有 DTO 使用业务编码表达项目、梁、工序和被替代记录，对 B 不暴露内部 ORM 关联对象。

## 10. Service 和接口

建议公开入口：`database_services.process_records`。

| 方法 | 作用 |
|---|---|
| `record(data)` | 记录一次已经结束的工序执行，支持外部幂等 |
| `get(execution_code, project_code=...)` | 在项目范围读取单条记录 |
| `list(filters, page_request, sort_by, sort_order)` | 条件筛选和页码分页 |
| `void(execution_code, data, project_code=...)` | 受控作废，重复调用幂等 |

不提供 `update`、`delete`、`set_active`、`start`、`complete` 或任意状态赋值接口。

公开 Protocol、组合工厂和实现类只返回 DTO。B 不依赖 CRUD、ORM、Session 或表结构。

## 11. 查询规则

### 11.1 筛选条件

第一版支持：

- 项目编码；
- 梁编码；
- 工序编码；
- 多个执行结果；
- 多个来源；
- 开始时间范围；
- 结束时间范围；
- 是否作废；
- 是否为修正记录；
- 操作用户 ID；
- 外部记录标识；
- 执行编码、梁编码、操作人名称和备注关键词。

### 11.2 分页和排序

- 使用页码分页，页大小为 1 至 100；
- 默认 `finished_at DESC, id DESC`；
- 其他排序字段也必须追加同方向 `id`，保证相同值下顺序稳定；
- 不允许 B 传入任意数据库字段名；
- 第一版不提供游标增量查询。数字孪生的梁状态和梁位增量继续使用 V5 生命周期事件。

## 12. 事务与并发

### 12.1 创建

一次 `record` 使用一个事务完成引用解析、幂等检查、数据校验、插入和 DTO 转换。任何步骤失败均回滚，不留下半条记录。

并发重复创建由唯一约束兜底。若唯一冲突来自相同幂等键，Service 在新事务中读取既有记录并比较稳定业务字段，内容一致则返回，内容不同则抛出冲突异常。

### 12.2 作废

作废时使用 `SELECT ... FOR UPDATE` 锁定目标执行记录，再判断项目范围和作废状态。第一次作废写入作废字段；并发或后续重复作废读取并返回第一次结果。

### 12.3 不产生隐式副作用

创建和作废均不自动修改梁、不写质量记录、不写 V5 生命周期事件，也不自动调用 V3 审计。B 可以在业务操作成功后显式记录操作审计。

## 13. 异常契约

新增：

- `BeamProcessExecutionNotFoundError`，代码 `beam_process_execution_not_found`。

复用：

- `ProjectNotFoundError`；
- `BeamNotFoundError`；
- `ProcessDefinitionNotFoundError`；
- `UserNotFoundError`；
- `InactiveResourceError`；
- `ResourceAlreadyExistsError`；
- `ResourceConflictError`；
- `InvalidDataError`；
- `DatabaseUnavailableError`。

跨项目读取、作废或替代统一表现为工序执行记录不存在。底层 `IntegrityError`、锁异常和 PyMySQL 异常不直接暴露给 B。

## 14. 测试要求

V6 至少覆盖：

1. 三种结果正常创建和 DTO 字段；
2. 项目梁使用同项目工序或通用工序；
3. 全局梁只能使用通用工序；
4. 跨项目梁、工序和替代记录拒绝；用户是系统级资源，A 只校验存在性；
5. 停用工序不能创建新记录，历史记录仍可查询；
6. 同一梁同一工序允许多次执行；
7. 结束时间早于开始时间被拒绝；
8. 用户名称自动快照和外部人员名称；
9. 相同外部幂等键内容一致返回既有记录；
10. 相同幂等键内容不同返回冲突；
11. 并发幂等请求只保存一条；
12. 受控作废、重复作废和并发作废；
13. 替代记录范围、已作废前提、唯一性和循环保护；
14. 页码、筛选、关键词和稳定排序；
15. 创建或作废失败完整回滚；
16. 不修改梁状态、不新增生命周期事件；
17. 公开接口不暴露 ORM，不存在任意更新和删除；
18. Alembic 升级、降级、重新升级和模型一致性；
19. V1 至 V5 全量回归；
20. wheel 包含 V6 文件和迁移，公开导入路径有效。

## 15. 迁移和部署

V6 使用一份新的前向迁移创建表、外键、检查约束和索引，不修改已有业务表和历史数据。降级只删除 V6 新表，不触碰 V1 至 V5 数据。

部署顺序：

1. 停止使用未冻结 V6 契约的写入方；
2. 备份并升级数据库；
3. 部署同版本 Python 包；
4. 启动 B 的 V6 适配；
5. 验证创建、查询和作废；
6. 记录实际迁移版本和测试结果。

V6 第一版没有历史数据回填，也不根据现有 `beam.status` 推造工序执行记录。

## 16. 后续变化策略

- 需要计划和进行中状态时，新增生产任务模型，不向执行事实表添加任务状态机。
- 需要工序参数时，优先增加有明确类型的专用明细表，不使用无限扩展 JSON。
- 需要严格保存当时工序名称时，通过迁移增加快照字段。
- 需要与质量检查关联时，由 V7 增加可空执行记录外键，不反向修改 V6 核心含义。
- 需要驱动梁状态时，单独设计事务和状态映射，不在 `record` 中隐式追加。
- 新增结果或来源代码时保留旧代码的历史读取能力。

## 17. 编码前确认结论

若没有新的业务资料，V6 默认按以下结论开发：

1. 只记录已经结束的工序执行，不记录计划中或进行中任务；
2. 三种结果均要求开始和结束时间；
3. 同一梁同一工序允许重复执行；
4. 不校验工序顺序，不自动修改梁状态；
5. 错误记录采用作废加新记录，不允许原地修改；
6. 外部幂等键可空，但非人工来源建议必填；
7. 第一版只有页码查询，没有增量游标；
8. V6 只开发 A 的数据能力，不开发 B 的业务流程。

这些结论已经确认。V6 实现、数据字典、测试和 A-B 接口必须与本页保持一致；规则变化时先更新本页的变更记录，再修改数据库契约。
