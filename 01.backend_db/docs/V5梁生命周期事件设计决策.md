# 智能建梁数字孪生平台数据库 V5 梁生命周期事件设计决策

- 文档状态：已随 6.0.0 基线本地冻结
- 冻结标签：`backend-db-v6.0.0`
- 目标迁移：`d4a6f8b0c217`

## 1. 目标和范围

V5 在 V4 冻结版本基础上增加梁生命周期事件历史，用于保存梁创建、状态变化和梁位变化事实，并为 B 模块和数字孪生平台提供稳定的历史查询及游标增量读取能力。

V5 只实现 A 模块负责的数据模型、迁移、DTO、CRUD、Service、公开 Python 接口、测试和数据字典。V5 不实现 HTTP、登录鉴权、消息队列、WebSocket、MQTT、设备控制、页面、消费确认或客户端状态管理。

## 2. 核心设计

1. 使用专用只追加表 `beam_lifecycle_event`，不建立通用事件平台。
2. 事件项目归属跟随梁。为兼容 V1 全局梁，`project_id` 允许为空。
3. V5 不回填上线前历史，只记录 V5 上线后由 A 模块成功提交的变化。
4. 事件与对应的梁创建、状态变化或梁位变化在同一事务内提交或回滚。
5. 不使用 SQLAlchemy ORM 事件监听器。Service 在明确的业务操作点调用内部事件记录函数，保持事务边界可见。
6. 事件不提供创建、更新、删除、启停或归档公开接口。B 只能读取，不能自行伪造生命周期事件。
7. 操作人、请求地址、权限和结果摘要继续由 V3 `operation_audit_log` 负责，不复制到生命周期事件。
8. 事件类型和梁状态继续使用可扩展字符串及 Python 枚举，不使用 MySQL ENUM。
9. 同一项目范围内的事件写入在事务中串行化，保证事件 ID 顺序与提交顺序一致；不同项目互不阻塞。

## 3. 第一版事件类型

| 事件代码 | 含义 | 状态字段 | 梁位字段 |
|---|---|---|---|
| `BEAM_CREATED` | 梁建档成功 | `status_after` 保存初始状态 | 均为空 |
| `STATUS_CHANGED` | 梁状态实际发生变化 | `status_before`、`status_after` 必填且不同 | 均为空 |
| `POSITION_ASSIGNED` | 无梁位的梁进入梁位 | 状态字段为空 | 原梁位为空，目标梁位必填 |
| `POSITION_MOVED` | 梁从一个梁位移动到另一梁位 | 状态字段为空 | 原梁位、目标梁位必填且不同 |
| `POSITION_RELEASED` | 梁离开当前梁位 | 状态字段为空 | 原梁位必填，目标梁位为空 |

第一版不记录梁位工单创建、开始或取消，因为这些操作没有改变梁本身。梁位工单完成时只记录对应的一条梁位变化事件，并通过可空 `work_order_id` 关联来源工单，不额外记录“工单完成”生命周期事件。

## 4. 记录时机

生命周期事件只在以下 A 模块 Service 操作成功时自动生成：

- 创建梁；
- 梁状态实际变化；
- 直接分配梁位；
- 直接移动梁位；
- 直接释放梁位；
- 完成 `PLACE`、`MOVE` 或 `RELEASE` 梁位工单。

普通资料更新不生成生命周期事件。状态值未变化或梁位未变化时不生成事件。任一业务校验、数据库约束或提交失败都会使梁变更和事件一起回滚。

## 5. 数据结构

`beam_lifecycle_event` 保存以下最小信息：

- 技术主键 `id`；
- 可空项目外键 `project_id`；
- 梁外键 `beam_id`；
- 事件类型 `event_type`；
- 变化前后状态 `status_before`、`status_after`；
- 原梁位和目标梁位外键 `source_position_id`、`target_position_id`；
- 可空来源工单外键 `work_order_id`；
- 业务发生时间 `occurred_at`；
- 记录创建时间 `created_at`。

所有外键使用 `RESTRICT`。事件表不设置 `updated_at`，因为记录创建后不可修改。

## 6. 查询接口

V5 公开只读的生命周期事件 Service，建议入口为 `database_services.beam_events`：

| 方法 | 用途 | 返回 |
|---|---|---|
| `get(event_id, project_code=...)` | 按 ID 读取单条事件 | `BeamLifecycleEventRead` |
| `list(filters, page_request, sort_by, sort_order)` | 管理端页码查询 | `PageResult[BeamLifecycleEventSummary]` |
| `list_after(filters, cursor_request)` | 数字孪生增量读取 | `CursorPageResult[BeamLifecycleEventSummary]` |

筛选条件限定为项目编码、梁编码、多个事件类型及发生时间范围。返回 DTO 使用业务编码表示项目、梁、梁位和工单，不向 B 暴露 ORM 或数据库 Session。

## 7. 游标增量读取

1. 增量读取按事件 `id` 升序排列；`occurred_at` 继续表达业务发生时间，不承担增量水位职责。
2. 游标对应的事件不重复返回，查询条件为严格大于游标位置。
3. `cursor=None` 从当前筛选范围内的第一条事件开始。
4. 游标采用带版本号的不透明 URL-safe Base64 字符串，当前版本只保存事件 ID。
5. 无效、损坏或版本不支持的游标转换为 A 模块稳定输入异常，不暴露底层解析错误。
6. 不同项目或不同筛选条件必须分别保存游标，游标不能混用。
7. A 保证已提交事件的稳定顺序读取，不提供消息投递、消费确认或 exactly-once 消费语义。B 应按事件 ID 幂等处理重试数据。
8. 同一项目或全局范围使用内部锁记录串行化事件 ID 分配，锁仅持有到当前业务事务提交或回滚；该内部表不属于 B 的公开契约。
9. V5 修复前的旧版游标不兼容。部署时应停止旧写入方，先完成迁移再统一重启；开发环境已有游标应重置。

## 8. 索引设计

- `(project_id, occurred_at, id)`：按发生时间查询项目历史；
- `(beam_id, occurred_at, id)`：单梁生命周期查询。
- `(project_id, id)`：项目增量读取。

内部表 `beam_lifecycle_event_stream_lock` 仅保存项目或全局范围键，用于事务锁定，不保存业务数据，也不对 B 暴露。

第一版不为 `event_type` 单独建立索引。待真实查询量证明有必要后再通过迁移增加，避免无依据增加写入成本。

## 9. 一致性约束

Service 必须保证：

- 事件、梁、梁位和来源工单属于同一项目作用域；
- 全局梁只能生成 `project_id IS NULL` 的全局事件；
- 状态事件的前后状态真实对应本次变化；
- 梁位事件的原梁位和目标梁位真实对应本次变化；
- `work_order_id` 只在梁位工单完成生成的梁位事件中填写；
- 每次实际梁变化只追加一条生命周期事件。

## 10. 测试与审计要求

V5 至少验证：

- 五类事件的字段形状和记录时机；
- 状态或梁位未变化时不生成事件；
- 业务失败和提交失败时事件回滚；
- 直接梁位操作和工单完成不会重复记录；
- 项目隔离和全局数据兼容；
- 页码筛选、稳定排序和游标边界；
- 相同 `occurred_at` 下依靠 `id` 连续读取，不重复、不遗漏；
- 同一项目并发事务不会使游标越过较晚提交的事件；
- 不同项目的事件写入互不阻塞，事务回滚后锁可正常释放；
- 损坏游标和跨筛选范围误用的约束说明；
- 公开接口不暴露 ORM，不提供事件写入、更新或删除；
- V1 至 V4 全量回归及 Alembic upgrade/downgrade 往返。

## 11. 后续扩展边界

设备事件、告警、时序测点、运输轨迹、消息投递和通用数据同步不进入 V5。以后新增事件类型时优先扩展稳定代码和可空关联字段；只有出现明确的跨领域共同需求后，才评估独立事件平台或 Outbox，不提前建设通用框架。
